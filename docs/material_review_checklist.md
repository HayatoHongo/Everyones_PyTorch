## 教材レビュー項目

**前提：実際に空欄を埋めながら、コードを最後まで動かす。**
**教材作成者自身が、教えてる内容を少なくとも1ヶ月以上以前に学習済みであり、技術的な正誤を判断する能力があること。**

### 優先順位の定義

* **A：時間がなくても必ず確認・修正する**
* **B：時間がなければ飛ばしてよい。**

---

## A：時間がなくても必ず確認・修正する項目

### A.1 解説が不足していないか

新入生が習っていない知識や用語を、説明なしで使っていないか。

レビューする側が少しでも迷う部分には、解説を追加する。

解説の重複は良い復習になる。
不足を恐れ、余剰を恐れない。

---

### A.2 コードセルは「1処理＋表示」を基本とする

コードセルは、原則として1つの処理だけを行う。

基本形は、処理を1行で実行し、その結果を次の行で表示する形式とする。

```python
Y_pred = X @ W
print_formatted_tensor("Y_pred", Y_pred)
```

原則として、

**1コードセル = 1処理**

とする。

ただし、以下の場合は例外とする。

* 複数の処理をまとめた方が、処理の意味を理解しやすい場合
* 一連の処理をまとめて確認するまとめセル
* 分割すると、かえってコードの流れが分かりにくくなる場合

---

### A.3 技術的な正しさ

教材作成者自身が、教えてる内容を少なくとも1ヶ月以上に学習済みであり、技術的な正誤を判断する能力があること。その上で、Notebook全体を強力なコーディングエージェントに読み込ませ、技術的な誤りや見落としがないか確認する。

A.4 読者がそれまでに身につけた知識では理解できないことをいきなり示してはいけない。

例えば、記号の意味すら読者に伝わっていない段階で、数式を示してはいけない。特にセクションの冒頭で目的を示す場合には注意。仮に、「中身をすぐに理解して欲しいわけじゃないが、とりあえず数式を見せる」ためであってもこれは認められない。読者はそうした曖昧なニュアンスを理解してくれないし、中身をすぐに理解しようと試みてしまう。セクション冒頭でセクションの目的を示す場合は、読者がすぐに理解できる範囲で示すか、あるいは「現時点で意味がわからなくても大丈夫です。これを理解することが最終目標です」と曖昧さを完全に排除してストレートに表現する。

---

## B：時間がなければ飛ばしてよい項目

### B.1 答えありきの解説になっていないか

手順だけでなく、「なぜその発想になるのか」まで説明する。

例えば、
x^2-1=0

に対して、いきなり「因数分解して解きます」と説明しても、なぜ因数分解するのかが分からない。

「積が0なら、どちらかが0になる」という性質を使いたいので、
(x-1)(x+1)=0

の形に変える、という自然な流れを示す。

#### 例外

`loss.backward()` など、その処理に至る経緯を詳しく説明することが著しく困難な場合は除外する。

ただし、その場合も、説明せずに流すのではなく、現時点では内部の詳細を扱わないブラックボックス的な処理であることを明示する。

---

### B.2 数式を一気に出していないか

長い数式を一気に提示せず、理解できる単位に分けて順番に示す。

各部分を説明した後、最後に全体を統合する。

行列については、行列の各要素を示し、それぞれが何を意味するのかを解説する。

最初から総和記号 (\Sigma) は使わない。

まずは総和を展開し、それぞれの項が何を意味しているのかを説明する。

展開後の中身を十分に理解できる状態になった場合、または内容が明らかに簡単な場合にのみ、(\Sigma) を用いる。

---

### B.3 Markdownセルが長すぎないか

画面全体を覆うほど長いMarkdownセルを作らない。

説明の途中にコードセルを挿入し、内容を分割する。

コードセルを挿入することが難しい場合は、図や表を挿入して分割する。

ただし、分割することで説明の流れが不自然になる場合は、無理に分けなくてもよい。

---

### B.4 print文はシンプルになっているか

行列やテンソルの中身を表示する場合は、原則として、本郷の自作関数である `print_formatted_tensor` を用いる。

この関数はEveryonesLLMに登場するものを使用する。

```python
print_formatted_tensor("Y_pred", Y_pred)
```

それ以外の場合は、簡潔な `print` 文を使用する。

```python
print("x", x)
```

`x.item()` のように、表示のためだけに要素を取り出す処理は極力避ける。

```python
print("x", x.item())
```

よりも、

```python
print("x", x)
```

を優先する。

表示結果の綺麗さよりも、コード自体の分かりやすさを優先する。

---

### B.5 不必要な比喩を使っていないか

基本的に比喩は避ける。

難しい概念についても、比喩による曖昧な説明に頼らない。

代わりに、数値の小さいシンプルな疑似データを使い、実際の計算やコードを通して説明する。

B.6 まずは数式をハードコードする
例えば　softmax を説明するときに、いきなりtorch.softmaxのような便利な関数を使ってはいけない。e**(-z1) / e**.... のように、擬似データを用いて、数式通りにハードコードで計算する。特に、softmaxのように複数の値の出力がある場合は、2回以上、このハードコードでの具体例を示す。便利な関数を導入するのはその後。

B.7 数式の下には必ず記号の意味を示す。
数式の下には必ず記号の意味を示す。
長い数式は$$で囲むが、ただの記号は$で囲む。

B.8 セクションの冒頭では、そのセクションの最終目標を示す。
セクションの冒頭では、そのセクションの最終目標を示す。
ただし、読者がそれまでの知識で瞬時に理解できないような表現を交えてはいけない。
悪い例:「クロスエントロピーの数式はこれです、（読者が瞬時に理解できない数式）」
良い例: 「予測の分布と正解の分布のズレを見たい。そこで、二乗誤差ではなく、二クロスエントロピー誤差という新しい指標を導入する。」

B.9 数式はシンプルに。
数式は限りなくシンプルにする。特に、使う記号の数を少なくする。
ただ具体的な値を代入するだけの変数とかは不必要。
とにかく数式の理解の最大のボトルネックは記号の定義なので、
使う記号の数を少なくする。定義が読者にとってわかりやすい記号を優先的に残す。
